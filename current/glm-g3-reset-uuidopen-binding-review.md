## Ranked findings

### P2 SB-1 — A stale or wrong Reset binding can authorize UuidOpen

`scripts/g3_fault_protocol.py:875–894` stores every `SessionBound` before it checks a window. It does not compare Reset `auth` or `matched_input` to the installed probe and Reclaim. It accepts a slot binding that predates installation. `:1023–1029` then treats any stored binding in that slot as the Reset predecessor, using only the client number for the final comparison.

In both modes, independently validated event envelopes with wrong Reset auth and wrong matched input were accepted. A `SessionBound` at event9, followed by Reset installation at event10, UuidOpen installation at event11, and OPEN/durable/output at events12–14, produced a UuidOpen receipt **without any Reset Reclaim**. The receipt named the stale predecessor event9. A changed-attachment `SessionBound` correctly raised `reset binding differs from the observed reclaim identity`, but it had already replaced the stored attachment: generation3/connection50 became generation4/connection51. This is not fail-closed state publication.

Require a post-installation, authenticated, exact Reset input/key/attachment binding for the actual predecessor. Check all fields and order before publishing a slot. Reject a stale, foreign, mismatched or non-Reset predecessor without leaving usable state. The current passing unbound-predecessor test does not cover these cases.

### P2 SB-2 — The held OPEN can belong to a different attachment or commit

`scripts/g3_fault_protocol.py:965–997` joins a Journal to an OPEN input and matches queued output only by input and key. It does not compare `OutputTag.attachment` to the OPEN attachment or `OutputTag.cause` to the checked commit. In both modes, a queued output for connection51/generation4 bound to a SessionIdentity on connection50/generation3. A queued output with commit operation10 also bound to a checked Journal commit with operation9. Both produced ordinary offline UuidOpen receipts.

Source audit also shows that `TransportAccepted` closes the window without comparing its output ID, attachment, origin or summary to the held output. That particular mismatch is a source finding, not an additional executed probe. Bind and close only the exact typed output for the checked durable completion and current attachment. Reject foreign origins and changed output identity at both boundaries.

### P2 SB-3 — Distinct reclaim and receipt identities collapse

At `scripts/g3_fault_protocol.py:913–921`, duplicate comparison omits the reclaim ID and old target. Two validated Received events with the same input/key/attachment/flags but reclaim IDs1 and2 were treated as the same candidate. `bind_reset_reclaim` returned the first receipt instead of refusing the conflicting identity.

At `:1046–1056`, `join` checks the supplied boot, provenance, seam and UUID, but not the receipt's exact window event or identity. Two distinct same-boot model instances with the same UUID and different input/requester/reclaim produced a successful join of the first instance's receipt into the second. The returned event was12 although the local window opened at20. Cross-boot refusal itself passed. Compare the full candidate and receipt identity, and reject conflicting duplicates or foreign same-boot receipts. Do not choose the first candidate.

### P2 SB-4 — The observation bound is exceeded after refusal

At `scripts/g3_fault_protocol.py:843–845`, `_note` increments before it checks the limit. After 64 valid observations, the 65th raises `seam observation capacity`, but the counter remains65 and `bind_reset_reclaim` returns a receipt with `observations:65`. The interface therefore allows usable state above the stated maximum after the refusal.

The separate invalid-content limit-order probe filled eight window entries and passed a deliberately malformed ninth body. It observed one `deepcopy` before the capacity check and got `invalid integer: body.attachment.connection`, not `seam window capacity`. This probe intentionally goes outside the documented already-validated-envelope precondition; it tests the user's explicit limit+1/pre-validation requirement, not normal validated ingestion. With a valid ninth body, the existing `_window` guard did reject before inserting a ninth window. Preserve that narrower positive result. Check bounds before the relevant allocation or state mutation, and make capacity failure non-usable.
