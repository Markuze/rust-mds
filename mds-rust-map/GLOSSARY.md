# Glossary

> Part of the [Rust MDS reference set](README.md). Terms used in the [C++ MDS project map](cpp-map/README.md), each with a short definition and a link to the page that explains it. Definitions describe the C++ MDS and its peers at ceph.git commit `5f7e383ae6d` and the Linux 7.3.0-rc6 snapshot `af32da41b03`; they were checked against those pages and the code cited here.

## A

- **Admin socket and `tell`**: the two transports of the MDS command plane. The admin socket is a local Unix socket (`ceph daemon mds.<id> ...`); `tell` sends `MCommand` over the messenger (`ceph tell mds.<id> ...`, mgr modules through libcephfs) and needs `allow *` MDS caps. Both use one table of 60 MDS commands and 36 generic ones. → [admin commands 3.1 and 3.2](cpp-map/13-admin-and-config/admin-commands.md#31-transport-1-the-local-admin-socket)
- **Ambiguous authority**: a subtree root whose `dir_auth` pair has a second rank, `(a,b)`, while authority moves between ranks during an export; an exporter's frozen tree is `(a,a)`. Objects in such a region wait for single authority. Imports that were journaled but not finished when a rank failed are *ambiguous imports*, settled in resolve. → [subtrees 3.1.1](cpp-map/04-cache/mdcache-subtrees-traversal-replication.md#31-the-authority-model), [subtree migration 3.1](cpp-map/08-multi-mds/subtree-migration.md#31-vocabulary-and-the-dir_auth-pair)
- **`As` / `Ax`**: the two cap bits of `authlock` (shift 2): shared lets a client cache mode, uid, gid, btime and `fscrypt_auth`; exclusive lets it change them locally and flush them later (`src/include/ceph_fs.h:841 (CEPH_CAP_SAUTH)`). → [capabilities 3.1](cpp-map/02-client-protocol/capabilities.md#31-the-cap-bit-model)
- **Async dirops**: kernel client mode (on by default, `nowsync`) in which `open(O_CREAT)` and `unlink()` return before the MDS has processed the request, flagged `CEPH_MDS_FLAG_ASYNC` (`src/include/ceph_fs.h:586`). It needs `Fx` plus `Dc` (create) or `Dr` (unlink) on the directory, and delegated inode numbers for creates; the C++ MDS at this commit never grants `Dc`/`Dr`, so the kernel always falls back to synchronous requests. → [leases 3.4](cpp-map/02-client-protocol/leases-lock-caches-and-async-dirops.md#34-async-create-end-to-end), [leases 8 G1](cpp-map/02-client-protocol/leases-lock-caches-and-async-dirops.md#8-edge-cases-failure-handling-and-gotchas)
- **Auth and replica**: every cached object has one authoritative ("auth") rank, the only rank that changes it or starts a lock state change; other ranks may hold read copies (replicas). An inode belongs to the rank owning the dirfrag of its primary dentry; a dirfrag to its subtree's `dir_auth`. The `STATE_AUTH` bit caches the answer on each object. → [subtrees 3.1](cpp-map/04-cache/mdcache-subtrees-traversal-replication.md#31-the-authority-model)
- **Auth pin**: a per-object counter that keeps an authoritative object from being frozen, and therefore from being exported or fragmented, while a request depends on it. Remote auth pins are taken through `MMDSPeerRequest` `OP_AUTHPIN`. → [cdir 3.5](cpp-map/04-cache/cdir-cdentry-and-cache-objects.md#35-auth-pins), [acquiring locks 3.3](cpp-map/05-locking/acquiring-locks.md#33-acquire_locks-step-by-step)
- **`authlock`**: inode `SimpleLock` (`CEPH_LOCK_IAUTH`) for mode, uid, gid, btime and `fscrypt_auth`; it carries the `As`/`Ax` caps. → [lock types 3.2](cpp-map/05-locking/lock-types-and-state-machines.md#32-lock-types-per-object)

## B

- **Backtrace**: the `parent` xattr (`inode_backtrace_t`, `src/mds/inode_backtrace.h:58`) on an inode's first RADOS object, in the data pool for files and the metadata pool for directories, listing its ancestor dentries. It is written lazily when the log segment that dirtied it expires, and it is how `open_ino` and offline tools find an inode by number. → [cinode 3.11](cpp-map/04-cache/cinode-and-inode-types.md#311-backtraces), [RADOS object catalog 3.8](cpp-map/07-storage-formats/rados-object-catalog.md#38-backtraces-and-the-per-inode-object-0)
- **Balancer (`MDBalancer`)**: chooses which subtrees to move between ranks. Every metadata operation hits decayed popularity counters on the inode and its ancestors; when the file system flag `balance_automate` is set, rank 0 starts a heartbeat epoch every `mds_bal_interval` (10 s), ranks exchange loads with `MHeartbeat`, and each one exports its share through the Migrator. Export targets are published to the monitor with `MMDSLoadTargets`. → [balancer and pinning 3.1](cpp-map/08-multi-mds/balancer-and-pinning.md#31-big-picture)
- **Base inode**: an inode stored in its own `<ino>.00000000.inode` object instead of inside a dirfrag: the root (ino 1) and each rank's mdsdir (`0x100 + rank`). The global snaprealm inode (3) is also a base inode but exists only in memory. → [RADOS object catalog 3.3 and 3.6](cpp-map/07-storage-formats/rados-object-catalog.md#33-special-inode-numbers-and-ranges)
- **Beacon (`MMDSBeacon`)**: the message an MDS sends to the monitors every `mds_beacon_interval` (4 s) from its `mds-beacon` thread, carrying the state it wants, the last MDSMap epoch it saw, a sequence number, its compat set and its health metrics. The daemon stops beaconing when its internal heartbeat has not been reset within `mds_heartbeat_grace` (15 s), so the monitor replaces a wedged daemon. → [beacon and monitor 3.3 and 3.4](cpp-map/01-cluster-integration/beacon-and-monitor.md#33-the-mds-side-beacon-engine), [`mds_lock` analysis 1.1](cpp-map/00-architecture/mds_lock-analysis.md#11-definition-and-rules)
- **Blocklist (OSD blocklist)**: OSDMap entries that make OSDs refuse operations from an address with `-EBLOCKLISTED`. The monitor blocklists a failed MDS daemon (fencing), and the MDS blocklists evicted clients with `osd blocklist add`. → [RADOS and OSD 3.6](cpp-map/07-storage-formats/rados-and-osd-interactions.md#36-fencing-model), [sessions 3.8](cpp-map/02-client-protocol/sessions.md#38-eviction-paths-blocklisting-and-the-osd-epoch-barrier)

## C

- **Cap (capability)**: a per-(inode, client, rank) grant that lets a client cache or change part of an inode's state without asking the MDS each time, kept in a `Capability` object (`src/mds/Capability.h:74`). Its bits are a client-side projection of the four cap-bearing inode locks; the MDS issues them in replies and `MClientCaps` grants and revokes them before conflicting lock changes. Clients drop caps with `MClientCapRelease`. → [capabilities 1](cpp-map/02-client-protocol/capabilities.md#1-purpose-and-responsibilities)
- **Cap flush**: a client→MDS `MClientCaps` carrying metadata the client changed under exclusive caps (size, mtime, mode, xattrs). The MDS journals it as an `EUpdate` and answers with `FLUSH_ACK` for the flush tid after the commit; a flush with `FLAG_SYNC` makes the MDS flush its journal at once. → [capabilities 3.7](cpp-map/02-client-protocol/capabilities.md#37-dirty-metadata-flush-and-flush_ack)
- **`CDentry`**: the cache object for one name in a dirfrag, valid for a snapshot range `[first, last]`, with a primary, remote or null linkage, its dentry lock and versionlock, client leases and LRU membership (`src/mds/CDentry.h:76`). → [cdir 1](cpp-map/04-cache/cdir-cdentry-and-cache-objects.md#1-purpose-and-responsibilities)
- **`CDir` (dirfrag)**: the cache object for one directory fragment: the dentries whose name hash falls into one `frag_t`, with its `fnode_t`, dirty tracking, fetch from and commit to its `<ino>.<frag>` omap object, `dir_auth` and freeze state (`src/mds/CDir.h:48`). → [cdir 1](cpp-map/04-cache/cdir-cdentry-and-cache-objects.md#1-purpose-and-responsibilities)
- **cephx**: Ceph's shared-secret authentication. Monitors issue tickets; a client presents an authorizer on each connection, which the MDS verifies with rotating `mds` service secrets (it holds three). msgr2 crc mode binds the handshake to the session key and secure mode encrypts; the legacy msgr1 adds per-message signatures instead. → [transport 3.6](cpp-map/00-architecture/transport-auth-and-client-library-contract.md#36-cephx-on-the-service-side), [auth and MDS caps 3.2 and 3.3](cpp-map/01-cluster-integration/auth-and-mds-caps.md#32-how-the-mds-authenticates-itself)
- **CephFS feature bits**: a bitmap exchanged in session open (`CEPHFS_FEATURE_*`, bits 0 to 24 in this tree, `src/mds/cephfs_features.h:34-56`, `:58 (CEPHFS_FEATURES_ALL)`) that gates MDS behaviour per client. The MDSMap field `required_client_features` makes the MDS refuse sessions that lack listed bits. Bit 22 means `CHARMAP` here and `SUBVOLUME_METRICS` in Linux 7.1 and later. → [wire protocol 3.5](cpp-map/02-client-protocol/wire-protocol.md#35-cephfs-feature-bits-cephfs_feature_), [kclient expectations 7.1.4](cpp-map/02-client-protocol/kclient-expectations.md#714-the-bit-22-conflict)
- **`change_attr`**: a per-inode change counter that clients expose as the statx inode version and NFS change attribute; the MDS increments it on every ctime change, and directories derive theirs from their dirfrags' counters. → [POSIX contract 3.4](cpp-map/03-request-path/posix-semantics-contract.md#34-timestamps-and-change_attr)
- **Charmap**: per-directory name normalization and case-folding settings (`ceph.dir.charmap`, `casesensitive`, `normalization`, `encoding` vxattrs) stored in the inode's `optmetadata`. libcephfs applies them and sends the user's spelling as `alternate_name`; the MDS refuses most creates in such directories for sessions without feature bit 22. → [attributes and xattrs 3.8](cpp-map/03-request-path/attributes-and-xattrs.md#38-virtual-xattrs-set-and-remove-srcmdsservercc6342-serverhandle_client_setvxattr), [kclient expectations 7.1.4](cpp-map/02-client-protocol/kclient-expectations.md#714-the-bit-22-conflict)
- **`CInode`**: the cache object for one inode number over one snapshot range on one rank. It holds the `inode_t` (through `InodeStoreBase`), xattrs, fragtree, old inodes, eleven lock objects, the per-client cap table and the projection list (`src/mds/CInode.h:255`). → [cinode 3.1](cpp-map/04-cache/cinode-and-inode-types.md#31-object-model-at-a-glance)
- **Clientreplay (`up:clientreplay`)**: the recovery state in which a rank re-executes, one at a time, the requests that clients replayed with `CEPH_MDS_FLAG_REPLAY` because they had seen only an unsafe reply, before serving new requests. Pending NFS-Ganesha reclaims also hold a rank here. → [rank lifecycle 3.14](cpp-map/09-recovery/rank-lifecycle-and-recovery.md#314-clientreplay-upclientreplay)
- **Compat set (`CompatSet`)**: compat, ro-compat and incompat feature sets of a file system (in its MDSMap) and of each daemon (in its beacon). A standby whose incompat features the file system lacks is promoted only while the file system is upgradeable, and promotion merges the daemon's set into the file system's (`src/mds/FSMap.cc:821 (FSMap::get_available_standby)`, `:1032-1033 (FSMap::promote)`). → [FSMap and MDSMap 3.5](cpp-map/01-cluster-integration/fsmap-and-mdsmap.md#35-compatset-mechanics)
- **Completed requests**: the per-session record of finished request tids (with the inode number a create allocated), persisted in the SessionMap and in `EMetaBlob::client_reqs` and trimmed by the client's `oldest_client_tid`. It makes retried and replayed requests idempotent; it is kept per rank. → [request lifecycle 3.4](cpp-map/03-request-path/request-lifecycle.md#34-idempotency-reqid-and-completed-requests), [sessions 3.13](cpp-map/02-client-protocol/sessions.md#313-completed_requests-and-completed_flushes)
- **Copy-on-write (COW) of metadata**: every dentry and inode carries a `[first, last]` snapid range; before an object covered by a snapshot is changed, the old version is preserved as a snapped dentry, a snapped `CInode` or an `old_inodes` entry. → [snapshots 3.4](cpp-map/10-snapshots-quotas-subvolumes/snapshots.md#34-copy-on-write-of-metadata)

## D

- **Damage table (`DamageTable`)**: an in-memory, per-rank registry of metadata that could not be loaded or failed validation (dirfrags, dentries, backtraces, failed uninlines), consulted by `path_traverse` so requests fail fast with `-EIO`. It raises `MDS_DAMAGE`, some entries make the rank `down:damaged`, and it is lost on restart (`src/mds/DamageTable.h:125`). → [scrub and damage 3.16](cpp-map/11-background-services/scrub-and-damage.md#316-damagetable)
- **`Dc` / `Dr` (also written `Du`)**: map shorthand for `CEPH_CAP_DIR_CREATE` and `CEPH_CAP_DIR_UNLINK`, which reuse `Fc` and `Fr` on a directory (`src/include/ceph_fs.h:909-910`). They allow async create and async unlink in that directory and are issuable only after a lock cache exists, so the C++ MDS at this commit never grants them. → [leases 3.2.2](cpp-map/02-client-protocol/leases-lock-caches-and-async-dirops.md#322-how-dcdr-are-granted)
- **Delegated and preallocated inode numbers**: each session gets batches of `mds_client_prealloc_inos` (1000) inode numbers from the rank's InoTable so that creates can use them without a table update and can reply early. Part of a session's batch is delegated to kernel clients that advertise `DELEG_INO`, in create replies (`openc_response_t`), so they can number async creates themselves; at session close delegated numbers are purged (object 0 only) and returned. → [leases 3.3](cpp-map/02-client-protocol/leases-lock-caches-and-async-dirops.md#33-inode-number-preallocation-and-delegation), [sessions 3.14](cpp-map/02-client-protocol/sessions.md#314-preallocated-and-delegated-inode-numbers)
- **Dentry lease**: permission for a client to trust one cached dentry, positive or negative, for up to 30 s (`src/mds/MDCache.h:1198 (MDCache::client_lease_durations)`, only the 30 s pool is used). It is issued in reply traces (`LeaseStat`) and revoked with `MClientLease` when the dentry lock must change. → [leases 3.1](cpp-map/02-client-protocol/leases-lock-caches-and-async-dirops.md#31-dentry-leases)
- **Dentry linkage (primary, remote, null)**: a primary dentry owns its inode, which is stored inside the dentry's omap value; a remote dentry stores only `(ino, d_type, alternate_name)` and is a hard link to an inode whose primary dentry is elsewhere; a null dentry is a cached negative entry. → [cdir 3.12](cpp-map/04-cache/cdir-cdentry-and-cache-objects.md#312-cdentry-linkage-and-projection), [RADOS object catalog 3.5](cpp-map/07-storage-formats/rados-object-catalog.md#35-directory-fragment-objects-dirinofrag)
- **Dirstat (`frag_info_t`)**: the direct contents of a directory: number of files and subdirectories, mtime and `change_attr`. Each dirfrag keeps a `fragstat`, and the directory inode's `dirstat` is their sum, gathered under `filelock` (`src/include/cephfs/types.h:83 (frag_info_t)`). → [rstats 3.1 and 3.2](cpp-map/10-snapshots-quotas-subvolumes/rstats-quotas-and-subvolumes.md#31-the-two-statistic-families-and-where-they-live)
- **Discover (`MDiscover`, `MDiscoverReply`)**: the inter-MDS protocol by which a non-authoritative rank pulls replicas of dirfrags, dentries and inodes along a path from the authoritative rank. Each replica carries a nonce from the auth's replica map, used to recognize stale expiries. → [subtrees 3.6 and 3.7](cpp-map/04-cache/mdcache-subtrees-traversal-replication.md#36-discover-pull-replication)
- **dmClock**: the QoS algorithm (reservation, weight, limit) behind the optional `MDSDmclockScheduler`, which delays client requests per "volume", defined as the first three components of the session's mount root, on each rank separately. It is disabled by default (`mds_dmclock_enable`). → [QoS scheduler 1](cpp-map/12-qos-metrics-quiesce-quarantine/qos-dmclock-scheduler.md#1-purpose-and-responsibilities)

## E

- **Early reply (unsafe reply)**: the first `MClientReply` of a mutation, with `safe=0`, sent before the journal event is durable (`src/mds/Server.cc:2300 (Server::early_reply)`). Only the requesting client sees the projected state; it is suppressed, for example, when the inode number came from the InoTable or peers journaled. The safe reply follows the commit. → [request lifecycle 3.10 and 3.11](cpp-map/03-request-path/request-lifecycle.md#310-mutation-commit-pipeline-journal_and_reply)
- **`EMetaBlob`**: the after-image container embedded in most journal events: per-dirfrag lumps with the new `fnode_t`, full images of changed dentries and inodes, remote and null dentries, base inodes, table versions, client request ids and truncate markers (`src/mds/events/EMetaBlob.h:50`). Replay installs the images without version comparison. → [events and replay 3.4](cpp-map/06-journal/events-and-replay.md#34-emetablob-in-detail)
- **Ephemeral pin**: a hash-based placement policy on a directory. `ceph.dir.pin.distributed` force-splits the directory and spreads its dirfrags over ranks by a consistent hash; `ceph.dir.pin.random` pins a random fraction of descendant directories, capped by `mds_export_ephemeral_random_max` (0.01). → [balancer and pinning 3.13 and 3.14](cpp-map/08-multi-mds/balancer-and-pinning.md#313-distributed-ephemeral-pins-cephdirpindistributed)
- **`ESubtreeMap`**: the journal event that records the rank's whole subtree map (each authoritative subtree, its bounds and the spanning tree of dentries from the root) at the start of every major segment, so that replay can start there. → [subtrees 3.3](cpp-map/04-cache/mdcache-subtrees-traversal-replication.md#33-esubtreemap-journaling-the-subtree-map), [MDLog 3.12](cpp-map/06-journal/mdlog-and-journaler.md#312-segments-and-boundaries)
- **Eviction**: forced removal of a client session by the MDS. By default the client's address is blocklisted on the OSDs, its caps and file locks are dropped, and the rank's OSD epoch barrier is raised. → [sessions 3.8](cpp-map/02-client-protocol/sessions.md#38-eviction-paths-blocklisting-and-the-osd-epoch-barrier)
- **Export pin (`ceph.dir.pin`)**: a static assignment of a directory's subtree to one rank, applied on each tick by `handle_export_pins`; a negative value unpins. Pinned subtrees are not moved by the balancer. → [balancer and pinning 3.12](cpp-map/08-multi-mds/balancer-and-pinning.md#312-export-pins-cephdirpin)

## F

- **`F` caps (`Fs`, `Fx`, `Fr`, `Fw`, `Fc`, `Fb`, `Fl`)**: the eight-bit cap field of `filelock` (shift 8). `Fs` caches size, times and directory contents; `Fx` changes them locally; `Fr` and `Fw` read and write file data; `Fc` caches reads and `Fb` buffers writes; `Fl` allows lazy I/O and is issued only when wanted; `Fa` (extend) is defined but never granted (`src/include/ceph_fs.h:828-835, 844`). → [capabilities 3.1](cpp-map/02-client-protocol/capabilities.md#31-the-cap-bit-model)
- **Fencing**: keeping a failed MDS from writing. The monitor blocklists the old daemon's addresses and records `last_failure_osd_epoch` in the MDSMap; the replacement waits for that OSDMap before replaying the journal. → [RADOS and OSD 3.6](cpp-map/07-storage-formats/rados-and-osd-interactions.md#36-fencing-model), [beacon and monitor 3.10](cpp-map/01-cluster-integration/beacon-and-monitor.md#310-failover-and-fencing)
- **File layout (`file_layout_t`)**: stripe unit, stripe count, object size, pool and pool namespace of a file's data, inherited from the nearest ancestor directory layout at creation and changeable only while the file is empty; clients compute data-object names from it (`src/include/fs_types.h:107 (file_layout_t)`). → [attributes and xattrs 3.8](cpp-map/03-request-path/attributes-and-xattrs.md#38-virtual-xattrs-set-and-remove-srcmdsservercc6342-serverhandle_client_setvxattr)
- **File locks (fcntl and flock)**: advisory locks that the MDS arbitrates cluster-wide (`SETFILELOCK`, `GETFILELOCK`) in tables held only in MDS memory under the inode's `flocklock`. They are dropped when the owner's cap is removed and rebuilt from client reconnect after an MDS restart. → [lookup, readdir, open and file locks 3.11](cpp-map/03-request-path/lookup-readdir-open-and-file-locks.md#311-file-locks-fcntl-and-flock)
- **`filelock`**: inode `ScatterLock` (`CEPH_LOCK_IFILE`) with its own state table, covering size, times, layout and other file fields and carrying the `F` caps; on directories it also scatter-gathers the dirstat. → [lock types 3.2](cpp-map/05-locking/lock-types-and-state-machines.md#32-lock-types-per-object)
- **fnode (`fnode_t`)**: the per-dirfrag header record (version, fragstat and accounted fragstat, rstat and accounted rstat, scrub stamps), stored as the omap header of the dirfrag object (`src/mds/mdstypes.h:167`). → [RADOS object catalog 3.5](cpp-map/07-storage-formats/rados-object-catalog.md#35-directory-fragment-objects-dirinofrag)
- **Forward (`MClientRequestForward`)**: the message telling a client to resend a request to another rank, normally the authoritative one. The MDS never relays client requests itself, because completed-request records are per rank. → [request lifecycle 3.13](cpp-map/03-request-path/request-lifecycle.md#313-forwarding)
- **Fragmentation (split and merge)**: changing a directory's fragtree with the internal request `CEPH_MDS_OP_FRAGMENTDIR`: freeze the dirfrags, journal `EFragment` PREPARE, store the new objects, journal COMMIT, delete the old objects, journal FINISH. Splits are triggered by size (`mds_bal_split_size`, 10000) or temperature, merges by size. → [dirfrags 3.5 to 3.7](cpp-map/04-cache/dirfrags-and-fragmentation.md#35-when-splits-and-merges-are-triggered)
- **`frag_t` and fragtree**: a `frag_t` names a contiguous range of the 24-bit dentry-name hash space as (value, bits); a `fragtree_t` partitions one directory into leaf frags (`src/include/frag.h:81 (frag_t)`, `:186 (fragtree_t)`). The fragtree is held in `CInode::dirfragtree` and kept consistent across ranks by `dirfragtreelock`. → [dirfrags 3.1 to 3.4](cpp-map/04-cache/dirfrags-and-fragmentation.md#31-fragment-identifiers-frag_t)
- **Freeze**: a dirfrag or subtree state that refuses new auth pins and waits for existing ones to drain, giving a quiescent cut for export and fragmentation. → [cdir 3.6](cpp-map/04-cache/cdir-cdentry-and-cache-objects.md#36-freezing)
- **FSMap**: the monitor-owned, Paxos-versioned map of every file system (identified by its `fscid`, with its MDSMap), every MDS daemon including the shared standby pool, and the default compat set (`src/mds/FSMap.h:275`). Only the `MDSMonitor` writes it. → [FSMap and MDSMap 1](cpp-map/01-cluster-integration/fsmap-and-mdsmap.md#1-purpose-and-responsibilities)
- **fscrypt fields**: `fscrypt_auth`, `fscrypt_file` and the last-block payload, which the MDS stores as opaque bytes; encryption and the choice of encrypted names (sent with `alternate_name` when long) happen in clients. → [attributes and xattrs 3.3.6](cpp-map/03-request-path/attributes-and-xattrs.md#336-fscrypt-truncate-last-block-read-modify-write), [kclient expectations 3.19](cpp-map/02-client-protocol/kclient-expectations.md#319-fscrypt-and-alternate-names)
- **Full metadata pool**: the MDS issues its own RADOS ops with `FULL_FORCE` and ignores full flags; client-visible refusals depend only on the metadata pool's `FLAG_FULL`, which gates a fixed list of ops for sessions without the `f` MDS cap flag (they receive `EACCES`). → [RADOS and OSD 3.8](cpp-map/07-storage-formats/rados-and-osd-interactions.md#38-full-cluster-behaviour-enospc-paths)

## G

- **Gather**: the wait of an unstable lock state until incompatible local rd/wr/xlocks drain, clients acknowledge cap revocations, leases are released, replica ranks acknowledge with `MLock`, and any file recovery or scatter write-behind finishes. → [lock types 3.6](cpp-map/05-locking/lock-types-and-state-machines.md#36-the-gather-engine-lockereval_gather)
- **gid (`mds_gid_t`)**: the identity of one MDS daemon instance in the FSMap, equal to its MonClient global id; a restarted or respawned daemon is a new gid. → [beacon and monitor 1](cpp-map/01-cluster-integration/beacon-and-monitor.md#1-purpose-and-responsibilities)
- **Global snaprealm**: an in-memory realm on inode 3 (`CEPH_INO_GLOBAL_SNAPREALM`, `src/include/ceph_fs.h:59`) whose snapshot set is the whole snap table. Hard-linked inodes outside subvolumes join it (`PARENT_GLOBAL`), and its updates go to every session. → [snapshots 3.2](cpp-map/10-snapshots-quotas-subvolumes/snapshots.md#32-snap-realms)

## H

- **Hard link**: a remote dentry naming an inode whose primary dentry may be in another directory, subtree or rank; the target is found by `open_ino`. Links and renames across subvolumes return `EXDEV`; when the primary name is removed while links remain, the inode moves to a stray directory and is later reintegrated by an internal rename. → [`mds_lock` analysis 6.5](cpp-map/00-architecture/mds_lock-analysis.md#65-hard-links), [strays 3.9](cpp-map/11-background-services/strays-and-purge.md#39-hard-links-remote-evaluation-reintegration-and-migration)
- **Health metrics and checks**: the MDS computes `MDSHealthMetric`s in `Beacon::notify_health` and sends them in beacons; the monitor turns them into cluster health checks such as `MDS_TRIM`, `MDS_SLOW_REQUEST` and `MDS_CACHE_OVERSIZED`, and derives file-system checks (`FS_DEGRADED`, `MDS_ALL_DOWN`) from the FSMap. → [config, perf counters and health 3.5](cpp-map/13-admin-and-config/config-perf-counters-and-health.md#35-health-pipeline)

## I

- **Inline data and uninline**: a deprecated mode in which small file contents are stored in the inode. The kernel client moves them into the file's first object when it opens such a file for writing, and scrub converts the remaining inline data into RADOS objects ("uninline"). → [kclient expectations 3.21](cpp-map/02-client-protocol/kclient-expectations.md#321-setattr-inline-data-layouts), [scrub and damage 3.11](cpp-map/11-background-services/scrub-and-damage.md#311-data-uninlining)
- **Inode number (ino)**: the 64-bit identity of an inode. It is `st_ino`, part of NFS file handles, and the prefix of data-object names `<ino>.<objno>`. Rank r allocates from `[(r+1)<<40, (r+2)<<40)`, and `[0x100, 0x1000)` is reserved for MDS-private system inodes. → [RADOS object catalog 3.3](cpp-map/07-storage-formats/rados-object-catalog.md#33-special-inode-numbers-and-ranges)
- **`inode_t`**: the persistent inode record (mode, owner, size, times, layout, quota, recursive and directory stats, fscrypt fields, optional metadata), encoded as version 20 with compat 6 (`src/include/cephfs/types.h:771`). → [cinode 3.3 and 3.4](cpp-map/04-cache/cinode-and-inode-types.md#33-inode_t-field-reference)
- **InoTable**: the per-rank allocator of inode numbers, persisted as `mds<r>_inotable`, versioned and journaled as `inotablev`; it also refills sessions' preallocated batches (`src/mds/InoTable.h:26`). → [MDS tables 3.2](cpp-map/07-storage-formats/mds-tables.md#32-inotable-per-rank-inode-number-allocator)

## J

- **Journal (MDLog)**: the per-rank write-ahead log of metadata mutations (`src/mds/MDLog.h:74`). Events are queued under `submit_mutex`, encoded and appended by the `mds-log-submit` thread, written to RADOS when `MDLog::flush()` runs or a journal object fills, grouped into segments and replayed after a failure. → [MDLog 1](cpp-map/06-journal/mdlog-and-journaler.md#1-purpose-and-responsibilities)
- **Journal events (`LogEvent`)**: the records in the journal, 20 type ids implemented by 18 classes, among them `EUpdate` (a client or internal mutation), `ESession`, `EOpen`, `EPeerUpdate` and `ECommitted` (two-phase commit), `EExport`, `EImportStart` and `EImportFinish`, `EFragment`, `ETableServer` and `ETableClient`, `EPurged`, and the boundary events `ESubtreeMap`, `ESegment`, `ELid` and `EResetJournal`. → [events and replay 3.2](cpp-map/06-journal/events-and-replay.md#32-event-catalogue)
- **Journaler and JournalPointer**: `Journaler` is a generic append-only byte stream over RADOS objects `<ino>.<objno>` with a header in object 0, used by MDLog and the PurgeQueue (`src/osdc/Journaler.h:129`). The JournalPointer object `<0x400+rank>.00000000` names the rank's active (front) journal and, during a format rewrite, the back one. → [MDLog 3.2 to 3.4](cpp-map/06-journal/mdlog-and-journaler.md#32-rados-objects-and-naming)

## L

- **Laggy**: the monitor marks a daemon laggy (`laggy_since`) when its beacons stop for `mds_beacon_grace` (15 s) and replaces it if a standby exists. The MDS also considers itself laggy when beacon acks stop, and then defers all rank messages. → [beacon and monitor 3.9](cpp-map/01-cluster-integration/beacon-and-monitor.md#39-laggy-detection-and-replacement-policy)
- **`linklock`**: inode `SimpleLock` (`CEPH_LOCK_ILINK`) for the link count; it carries the `Ls`/`Lx` caps. → [lock types 3.2](cpp-map/05-locking/lock-types-and-state-machines.md#32-lock-types-per-object)
- **`LocalLockC`**: a lock class with no inter-rank protocol, used for the `versionlock` of inodes and dentries and for the `quiescelock` (`src/mds/LocalLockC.h:22`). → [lock types 1](cpp-map/05-locking/lock-types-and-state-machines.md#1-purpose-and-responsibilities)
- **Lock cache (`MDLockCache`)**: an MDS-internal set of locks and auth pins kept for one client's cap on one directory, for CREATE or UNLINK, and advertised to the client by `Dc`/`Dr`. At this commit none is ever created, because `Locker::create_lock_cache` requires the bit to be issued already (`src/mds/Locker.cc:1124-1128`). → [leases 3.2](cpp-map/02-client-protocol/leases-lock-caches-and-async-dirops.md#32-lock-caches)
- **Lock modes (rdlock, wrlock, xlock)**: rdlock is a shared read lock; wrlock is a shared write lock that lets several writers update scatter, file and local locks concurrently; xlock is exclusive, with one xlocker. After an early reply an xlock moves to `XLOCKDONE`, in which only the xlocking client may read the new value until the commit. → [acquiring locks 1](cpp-map/05-locking/acquiring-locks.md#1-purpose-and-responsibilities), [acquiring locks 3.5](cpp-map/05-locking/acquiring-locks.md#35-compatibility-of-rdlock-wrlock-and-xlock)
- **Lock states**: the states of the static tables in `src/mds/locks.c`. Stable states are `SYNC` (shared read on all ranks), `LOCK` (auth only), `EXCL` (exclusive caps for a loner), `MIX` (scatter and file locks only: concurrent writers on several ranks or clients) and `XSYN` (filelock); transitional states are named after both ends, such as `SYNC_LOCK`, and wait for a gather; xlocks pass through `PREXLOCK`, `XLOCK` and `XLOCKDONE` (`src/mds/locks.h:45-101`). → [lock types 3.3 and 3.4](cpp-map/05-locking/lock-types-and-state-machines.md#33-the-state-table-schema)
- **Locker**: the MDS component that acquires locks for requests, drives lock state transitions, issues and revokes caps, handles client cap messages, and manages leases and lock caches (`src/mds/Locker.h:58`). → [acquiring locks](cpp-map/05-locking/acquiring-locks.md), [lock types](cpp-map/05-locking/lock-types-and-state-machines.md)
- **LogSegment**: a run of journal events starting at a boundary event. It keeps intrusive lists of the objects its events dirtied, which must be written back before it can expire (`src/mds/LogSegment.h:45`). A major segment starts with `ESubtreeMap` (or `ELid`, `EResetJournal`); `ESegment` starts a minor one, and trimming expires whole major-segment groups. → [MDLog 3.12 and 3.13](cpp-map/06-journal/mdlog-and-journaler.md#312-segments-and-boundaries)
- **Loner**: the single client chosen to receive exclusive caps (`x` bits) on an inode (`CInode::loner_cap`). `CInode::calc_ideal_loner` picks the only non-stale client that wants a write cap or `Fr` on a file, or the only client of a directory without subtree-root dirfrags, and none while a replica rank wants caps. → [cinode 3.15](cpp-map/04-cache/cinode-and-inode-types.md#315-client-capability-tracking-on-the-inode), [lock types 3.1](cpp-map/05-locking/lock-types-and-state-machines.md#31-vocabulary)
- **LRU and trimming**: unpinned dentries sit in two LRU lists (`lru`, `bottom_lru`); the `mds-cache-trim` thread expires them so that the `mds_co` mempool stays near `mds_cache_memory_limit` (4 GiB), and recalls caps from clients when the cache is too full. → [cache lifecycle 3.2 to 3.5](cpp-map/04-cache/mdcache-lifecycle-trim-and-memory.md#32-lru-mechanics-srcincludelruh)
- **`Ls` / `Lx`**: the cap bits of `linklock` (shift 4), letting a client cache or change the link count. → [capabilities 3.1](cpp-map/02-client-protocol/capabilities.md#31-the-cap-bit-model)

## M

- **Mantle**: an optional, experimental balancer policy written in Lua, stored as a RADOS object named by the MDSMap field `balancer`, that replaces the default balancer's decision of how much load to send to which rank. → [balancer and pinning 3.9](cpp-map/08-multi-mds/balancer-and-pinning.md#39-mantle-lua-policy)
- **`max_size` and `client_ranges`**: the writeable byte range granted to each client that writes a file, stored in `inode_t::client_ranges` and shown to clients as `max_size`. It is journaled before a client may write past it, and it bounds file size recovery after a writer is lost. → [capabilities 3.9](cpp-map/02-client-protocol/capabilities.md#39-max_size-and-client_ranges)
- **MDS (`ceph-mds`)**: the CephFS metadata server daemon: it serves the namespace, inode attributes, caps, file locks, snapshots and quotas of a file system, while clients move file data directly to and from the OSDs. → [C++ MDS project map](cpp-map/README.md#1-purpose-and-responsibilities)
- **MDS auth caps (`MDSAuthCaps`)**: the `mds` capability string of a cephx entity, for example `allow rw fsname=a path=/x`, decoded from its ticket when a connection is accepted and evaluated by `MDSAuthCaps::is_capable` (`src/mds/MDSAuthCaps.cc:266`). It checks file system, path prefix, read and write, optional uid and gids, `root_squash`, flags and network, and it is the only permission check the MDS makes; clients also receive a reduced copy (`cap_auths`). → [auth and MDS caps 3.4 and 3.5](cpp-map/01-cluster-integration/auth-and-mds-caps.md#34-the-mds-cap-language)
- **MDS cap flags (`p`, `s`, `f`, `q`, `Q`)**: in an MDS cap, `p` allows setting layouts, quotas, pins and other `ceph.*` vxattrs; `s` allows creating, removing and renaming snapshots; `f` allows space-consuming metadata ops while the metadata pool is full; `q` and `Q` allow access to quarantined subvolumes and are never implied by `*`. → [auth and MDS caps 3.4](cpp-map/01-cluster-integration/auth-and-mds-caps.md#34-the-mds-cap-language)
- **MDS states**: `up:boot`, `up:standby`, `up:standby-replay`, `up:creating`, `up:starting`, `up:replay`, `up:resolve`, `up:reconnect`, `up:rejoin`, `up:clientreplay`, `up:active`, `up:stopping`, `down:stopped`, `down:damaged` and `down:dne`. The monitor assigns some of them; the MDS requests the others in beacons, and the monitor validates each transition. → [FSMap and MDSMap 3.3](cpp-map/01-cluster-integration/fsmap-and-mdsmap.md#33-mds-daemon-and-rank-states)
- **`mds_lock`**: the single `ceph::fair_mutex` per `ceph-mds` process (`src/mds/MDSDaemon.h:74`) under which all metadata state is read and changed. It is a FIFO ticket lock, not recursive, and every unlock wakes all waiters. → [`mds_lock` analysis 1.1](cpp-map/00-architecture/mds_lock-analysis.md#11-definition-and-rules)
- **MDCache**: the per-rank owner of cached `CInode`, `CDir` and `CDentry` objects, the subtree map, path traversal, replication, trimming and recovery bookkeeping (`src/mds/MDCache.h:158`). → [subtrees](cpp-map/04-cache/mdcache-subtrees-traversal-replication.md), [cache lifecycle](cpp-map/04-cache/mdcache-lifecycle-trim-and-memory.md)
- **`MDRequest` (`MDRequestImpl`)**: the state of one client, peer or internal request: its locks, auth pins and projected objects (from `MutationImpl`), its progress flags and its `metareqid_t` (client entity plus tid) under which it is registered in `active_requests` (`src/mds/Mutation.h:311`). → [request lifecycle 4](cpp-map/03-request-path/request-lifecycle.md#4-data-structures-and-invariants)
- **`MDSDaemon` and `MDSRank`**: the two halves of a `ceph-mds` process. `MDSDaemon` exists for the whole process and owns `mds_lock`, the timer, the beacon and the current MDSMap; `MDSRank` (created as `MDSRankDispatcher`) exists while the daemon holds a rank and owns every metadata subsystem (`src/mds/MDSDaemon.h:42`, `src/mds/MDSRank.h:170`). → [process and threading 3.3](cpp-map/00-architecture/process-and-threading.md#33-object-model-and-ownership)
- **mdsdir (`~mdsN`)**: the per-rank system directory, inode `0x100 + rank`, holding the rank's ten stray directories `stray0` to `stray9`. It is never fragmented and is invisible to clients. → [cache lifecycle 3.10](cpp-map/04-cache/mdcache-lifecycle-trim-and-memory.md#310-system-inodes-and-the-base-hierarchy)
- **MDSMap**: the per-file-system map consumed by MDS daemons and clients: ranks `in`, `up`, `failed`, `stopped` and `damaged`, the info of every daemon attached to the file system, `max_mds`, session timeouts, flags, pools, required client features and the compat set (`src/mds/MDSMap.h:68`). → [FSMap and MDSMap 4.1](cpp-map/01-cluster-integration/fsmap-and-mdsmap.md#41-mdsmap-fields)
- **Metadata pool and data pools**: a file system has one metadata pool, which holds all MDS-private objects (journals, dirfrags, tables), and one or more data pools, which hold file data written by clients plus the backtraces the MDS writes; the first data pool is the default. → [RADOS object catalog 1](cpp-map/07-storage-formats/rados-object-catalog.md#1-purpose-and-responsibilities)
- **Metrics (client metrics)**: performance data that clients send in `MClientMetrics` (cap hits, latencies, I/O sizes, per-subvolume I/O). Each rank forwards them to rank 0, whose `MetricAggregator` keeps labeled perf counters and answers mgr perf queries (`ceph fs perf stats`, `cephfs-top`); nothing is persisted. → [metrics 3.1](cpp-map/12-qos-metrics-quiesce-quarantine/metrics-and-subvolume-metrics.md#31-pipeline-overview)
- **mgr/volumes**: the ceph-mgr module that manages subvolume groups and subvolumes as directories under `/volumes/<group>/<name>/<uuid>` through libcephfs, setting the subvolume flag, quotas and pins with vxattrs and keeping its own `.meta` files. → [mgr, tools and orchestration 3.2](cpp-map/01-cluster-integration/mgr-tools-and-orchestration.md#32-mgrvolumes)
- **Migrator (export and import)**: moves authority over a subtree between ranks: the exporter freezes the subtree, ships its metadata, lock states and client caps in `MExportDir`, both sides journal (`EExport`, `EImportStart`, `EImportFinish`), and clients receive cap EXPORT and IMPORT messages. Bystander ranks that replicate the base dirfrag are told of the move. → [subtree migration 1](cpp-map/08-multi-mds/subtree-migration.md#1-purpose-and-responsibilities)
- **`MLock`**: the inter-MDS message that carries lock actions (`LOCK_AC_*`) and lock-state payloads between an object's authoritative rank and its replicas. → [lock types 3.11](cpp-map/05-locking/lock-types-and-state-machines.md#311-inter-mds-lock-protocol-mlock)
- **msgr1**: the legacy messenger protocol (banner `ceph v027`, `src/include/msgr.h:30`). Current peers do not use it: the kernel client speaks it only when mounted without an `ms_mode` option, and `mount.ceph` passes `ms_mode=prefer-crc` for the new device syntax. It supports per-message cephx signatures, which are on by default. → [transport 3.3](cpp-map/00-architecture/transport-auth-and-client-library-contract.md#33-msgr1-legacy-protocol)
- **msgr2**: the current messenger protocol (banner prefix `ceph v2\n`, `src/include/msgr.h:38`) with frames, crc and secure (AES-128-GCM) modes and optional compression; revision 2.1 is the only one the kernel supports. It is the protocol of current kernel mounts (`ms_mode=prefer-crc` from `mount.ceph`) and of the C++ clients. The C++ MDS binds msgr2 and msgr1 addresses by default. → [transport 3.4](cpp-map/00-architecture/transport-auth-and-client-library-contract.md#34-msgr20-and-msgr21)

## N

- **`nestlock`**: inode `ScatterLock` (`CEPH_LOCK_INEST`) whose state governs the recursive statistics (`rstat`); every namespace change wrlocks it on the parent directory. → [lock types 3.2](cpp-map/05-locking/lock-types-and-state-machines.md#32-lock-types-per-object), [rstats 3.6](cpp-map/10-snapshots-quotas-subvolumes/rstats-quotas-and-subvolumes.md#36-scatter-gather-of-dirstat-and-rstat-across-dirfrags-and-ranks)

## O

- **`old_inodes`**: the map of snapshot-era copies of an inode's record, kept on a multiversion inode: a directory, an inode with its own snaprealm or with more than one link, or one that already has old inodes (`src/mds/CInode.h:487-492 (CInode::is_multiversion)`). → [cinode 3.6](cpp-map/04-cache/cinode-and-inode-types.md#36-old-inodes-snapshot-era-copies)
- **`open_ino`**: finds an inode by number when it is not cached: ask the other ranks, then read backtraces from RADOS, then traverse the ancestors (`src/mds/MDCache.cc:9591 (MDCache::open_ino)`). NFS handles (`LOOKUPINO`), hard links and reconnect rely on it. → [subtrees 3.9](cpp-map/04-cache/mdcache-subtrees-traversal-replication.md#39-open_ino-finding-an-inode-by-number)
- **OpenFileTable (OFT) and Anchor**: the per-rank persistent set of open inodes and their ancestors, stored in `mds<r>_openfiles.<idx>` omap objects as `Anchor` records (ino, parent, name, `d_type`). It lets log segments expire without re-journaling open files and lets a recovering rank prefetch those inodes (`src/mds/OpenFileTable.h:47`). → [MDS tables 3.4](cpp-map/07-storage-formats/mds-tables.md#34-openfiletable)
- **OSD epoch barrier**: an OSDMap epoch that clients must reach before using caps issued after an eviction. The MDS raises it when it blocklists a client and sends it in cap messages; a client's barrier newer than the MDS's own map pauses all MDS RADOS operations until that map arrives. → [RADOS and OSD 3.7](cpp-map/07-storage-formats/rados-and-osd-interactions.md#37-the-osd-epoch-barrier)

## P

- **`p` (PIN cap)**: cap bit 0, `CEPH_CAP_PIN` (`src/include/ceph_fs.h:824`), which keeps an inode in the client's cache without any other permission. → [capabilities 3.1](cpp-map/02-client-protocol/capabilities.md#31-the-cap-bit-model)
- **Past parents (`past_parent_snaps`)**: snapshot ids an inode inherited from realms it was moved out of, recorded in its own `sr_t` when it leaves a realm that has snapshot history. The legacy `past_parents` map is decoded but not used. → [snapshots 3.2](cpp-map/10-snapshots-quotas-subvolumes/snapshots.md#32-snap-realms)
- **`path_traverse`**: `MDCache::path_traverse` (`src/mds/MDCache.cc:8443`) resolves a base inode number plus a relative path to cache objects, taking per-component locks as requested, fetching dirfrags, discovering replicas or forwarding when the rank is not authoritative. → [subtrees 3.5](cpp-map/04-cache/mdcache-subtrees-traversal-replication.md#35-path-traversal-path_traverse-srcmdsmdcachecc8443-mdcachepath_traverse)
- **Peer request (`MMDSPeerRequest`)**: an inter-MDS request made by the leader (the rank executing a client request) to a peer rank: remote auth pins, remote wrlocks and xlocks, and the prepare, commit and abort steps of cross-rank link, unlink, rmdir and rename. → [request lifecycle 3.19](cpp-map/03-request-path/request-lifecycle.md#319-peer-request-framework)
- **Pin (cache reference)**: a named reference count (`PIN_*`) on a cache object that keeps it from being trimmed; pins propagate up the tree. → [cdir 3.2](cpp-map/04-cache/cdir-cdentry-and-cache-objects.md#32-reference-counting-and-pins)
- **`policylock`**: inode `SimpleLock` (`CEPH_LOCK_IPOLICY`) for layout, quota, export pins, flags and optional metadata; ancestors are rdlocked through it for layout inheritance. → [lock types 3.2](cpp-map/05-locking/lock-types-and-state-machines.md#32-lock-types-per-object)
- **Projection**: read-copy-update of metadata. A mutation copies the newest projected `inode_t` or `fnode_t`, edits the copy, journals it, and after the commit the oldest projection is popped and becomes the stable version. → [cinode 3.7](cpp-map/04-cache/cinode-and-inode-types.md#37-projection-mechanics-read-copy-update), [cdir 3.8](cpp-map/04-cache/cdir-cdentry-and-cache-objects.md#38-versions-projection-and-dirty-tracking)
- **PurgeQueue and PurgeItem**: the per-rank, RADOS-journaled queue (objects `<0x500+rank>.<n>`) of `PurgeItem`s describing the objects to delete for purged strays; its own thread and lock execute them asynchronously under throttles (`src/mds/PurgeQueue.h:128`). → [strays and purge 3.5 to 3.7](cpp-map/11-background-services/strays-and-purge.md#35-enqueue-and-purgeitem-construction)

## Q

- **Quarantine**: an administrator-initiated, persistent block of client access to one subvolume, stored in the subvolume root's `optmetadata`. Sessions whose MDS caps carry `q`/`Q` keep access. For all other sessions, requests from quarantine-aware clients (feature bit 24) fail with `EACCES`, requests from unaware clients are parked until the quarantine is lifted, and every cap except `p` is revoked. → [quarantine 1](cpp-map/12-qos-metrics-quiesce-quarantine/quarantine.md#1-purpose-and-responsibilities)
- **Quiesce (QuiesceDb, quiesce set)**: a pause of metadata mutations and client writes under a set of paths on every active rank, used for consistent snapshots of several subvolumes. A QuiesceDb leader chosen by the monitor keeps the sets (states such as `QUIESCING`, `QUIESCED`, `RELEASING`, `RELEASED`), and per-rank agents quiesce each inode with an internal request. → [quiesce 3.1 to 3.4](cpp-map/12-qos-metrics-quiesce-quarantine/quiesce.md#31-architecture-overview)
- **`quiescelock`**: a per-inode local lock implicitly wrlocked, once per `acquire_locks` call, by mutations that take a cap-related wrlock or xlock, and xlocked by `QUIESCE_INODE` requests to hold such mutations off. → [quiesce 3.13](cpp-map/12-qos-metrics-quiesce-quarantine/quiesce.md#313-the-quiescelock-and-how-it-blocks-mutations)
- **Quota and quota realm**: `ceph.quota.max_bytes` and `ceph.quota.max_files` stored in a directory's `inode_t::quota`. Setting one makes the directory a snaprealm root so that clients find it by walking realms; only clients enforce quotas, using usage the MDS pushes with `MClientQuota`. → [rstats 3.9 to 3.11](cpp-map/10-snapshots-quotas-subvolumes/rstats-quotas-and-subvolumes.md#39-quotas-data-model-and-how-a-quota-is-set)

## R

- **Rank**: a metadata shard of a file system, numbered `0` to `max_mds - 1` (at most `MAX_MDS` = 0x100, `src/include/cephfs/types.h:41`) and held by at most one daemon at a time. A rank owns its subtrees, journal, InoTable range, SessionMap and stray directories. → [rank lifecycle 1](cpp-map/09-recovery/rank-lifecycle-and-recovery.md#1-purpose-and-responsibilities)
- **Reclaim (session reclaim)**: the protocol (`CEPH_MSG_CLIENT_RECLAIM`) by which a restarted NFS-Ganesha instance, identified by the `uuid` in its session metadata, destroys the session of its previous incarnation so its caps and locks are released at once; only `CEPH_RECLAIM_RESET` exists (`src/include/ceph_fs.h:378`). → [sessions 3.9](cpp-map/02-client-protocol/sessions.md#39-reclaim-protocol-nfs-ganesha-via-libcephfs)
- **Reconnect (`up:reconnect`)**: the recovery state in which clients send `MClientReconnect` with their caps, snaprealms, file locks and paths, within `mds_reconnect_timeout` (45 s). Sessions that do not reconnect are evicted, except sessions with a `timeout` metadata key (NFS-Ganesha), which are kept for reclaim. → [sessions 3.10](cpp-map/02-client-protocol/sessions.md#310-reconnect-protocol-mds-failover), [rank lifecycle 3.12](cpp-map/09-recovery/rank-lifecycle-and-recovery.md#312-reconnect-upreconnect-the-client-window)
- **RecoveryQueue (file size recovery)**: after a failover, files that were open for writing by clients that did not come back have their size and mtime recovered by probing their data objects up to `max_size`. → [rank lifecycle 3.16](cpp-map/09-recovery/rank-lifecycle-and-recovery.md#316-file-size-and-mtime-recovery-recoveryqueue)
- **Rejoin (`up:rejoin`)**: the recovery state in which ranks exchange `MMDSCacheRejoin` messages (weak from recovering ranks, strong from survivors) to rebuild replica and lock state, and attach the caps that clients reported in reconnect to inodes. → [resolve and rejoin 3.9 to 3.13](cpp-map/09-recovery/resolve-and-rejoin.md#39-rejoin-start-and-cap-matching-round-1)
- **Replay (`up:replay`)**: the rank reads its journal from the expire position and applies every event in order to rebuild its cache, subtree map, sessions and tables; replay writes nothing to RADOS. → [events and replay 3.5](cpp-map/06-journal/events-and-replay.md#35-replay-pipeline), [MDLog 3.15](cpp-map/06-journal/mdlog-and-journaler.md#315-replay-upreplay)
- **Resolve (`up:resolve`)**: the recovery state, multi-rank only, that settles subtree authority (including ambiguous imports) and the outcome of cross-rank two-phase commits that were in doubt, and resynchronizes the snap table. → [resolve and rejoin 3.4 to 3.6](cpp-map/09-recovery/resolve-and-rejoin.md#34-resolve-step-1-peer-resolves-two-phase-commit-outcomes)
- **`root_squash`**: an MDS cap qualifier: the grant cannot be used for writes by a caller with uid 0 or gid 0. → [auth and MDS caps 3.4](cpp-map/01-cluster-integration/auth-and-mds-caps.md#34-the-mds-cap-language)
- **rstat (`nest_info_t`)**: recursive totals of a subtree: bytes, files, subdirectories, snapshots and the newest ctime (`rctime`, which only moves forward) (`src/include/cephfs/types.h:144`). The MDS propagates a change eagerly to the parent and lazily above it, and clients read the values as `ceph.dir.r*` vxattrs or as directory sizes. → [rstats 3.1 to 3.5](cpp-map/10-snapshots-quotas-subvolumes/rstats-quotas-and-subvolumes.md#31-the-two-statistic-families-and-where-they-live)

## S

- **Safe reply**: the final `MClientReply` of a request (`safe=1`); for a mutation it is sent only after the journal event is durable. → [request lifecycle 3.11](cpp-map/03-request-path/request-lifecycle.md#311-replies)
- **ScatterLock and scatter-gather**: the lock class for data that several ranks update at once and the authoritative rank sums back: `nestlock`, `dirfragtreelock`, and `filelock` with its own table (`src/mds/ScatterLock.h:26`). Dirfrag auths accumulate deltas and the inode auth gathers them on a lock transition and journals the result. → [lock types 3.12](cpp-map/05-locking/lock-types-and-state-machines.md#312-scattergather-of-dirstat-rstat-and-dirfragtree)
- **Scrub (forward scrub)**: an administrator-triggered online walk of the namespace (`ScrubStack`, started on rank 0) that compares on-disk metadata with the cache (backtraces, base inodes, dirstat and rstat, snapshot bounds), can repair some of it, tags inodes and uninlines data. → [scrub and damage 3.1 to 3.10](cpp-map/11-background-services/scrub-and-damage.md#31-starting-a-scrub)
- **Session**: the relationship between one client entity and one rank (`src/mds/SessionMap.h:73 (Session)`), in state closed, opening, open, closing, stale or killing. A session not renewed within `session_timeout` (60 s) can become stale (by default only while the MDS is revoking caps from it or waiting for its flush), and a client silent for `session_autoclose` (300 s) is evicted (`src/mds/MDSMap.h:605-606`). → [sessions 3.2](cpp-map/02-client-protocol/sessions.md#32-state-machine), [sessions 3.6](cpp-map/02-client-protocol/sessions.md#36-renewal-staleness-autoclose)
- **SessionMap**: the per-rank container of sessions, persisted as the omap object `mds<r>_sessionmap`, with one rank-wide projected and committed version chain (`src/mds/SessionMap.h:576`). → [sessions 3.15](cpp-map/02-client-protocol/sessions.md#315-persistence-the-sessionmap-object-versions-and-journal-events)
- **`SimpleLock`**: the base lock class with shared-read and exclusive-write semantics, used for the dentry lock and for `authlock`, `linklock`, `xattrlock`, `snaplock`, `flocklock` and `policylock` (`src/mds/SimpleLock.h:80`). → [lock types 3.4.1](cpp-map/05-locking/lock-types-and-state-machines.md#341-sm_simplelock-srcmdslocksc15-45-dn-iauth-ilink-ixattr-isnap-iflock-ipolicy)
- **`.snap` directory**: the virtual directory through which clients list and access snapshots. The MDS never sees its name: clients send it as an empty path component, which `path_traverse` maps to `CEPH_SNAPDIR`; the name is a client option. → [snapshots 3.5](cpp-map/10-snapshots-quotas-subvolumes/snapshots.md#35-the-snap-directory-and-snapshot-paths)
- **Snap realm (`SnapRealm`, `sr_t`)**: a subtree that shares one set of snapshots, attached to an inode; `sr_t` is its persistent part (`src/mds/SnapRealm.h:32`, `src/mds/snap.h:88`). Realms exist for the root, mdsdirs, directories with snapshots, quota roots, subvolume roots and inodes that moved out of a realm with history. → [snapshots 3.2](cpp-map/10-snapshots-quotas-subvolumes/snapshots.md#32-snap-realms)
- **Snap table (`SnapServer`, `SnapClient`)**: the cluster-wide table of snapshots (`mds_snaptable`) served by rank 0 and cached on every rank. Snapshot creation, removal and renaming go through the generic table two-phase commit (prepare, agree, commit, ack), and removed snapshots are reported to the monitor so OSDs trim clones. → [snapshots 3.1](cpp-map/10-snapshots-quotas-subvolumes/snapshots.md#31-snapshot-ids-and-the-global-snap-table), [MDS tables 3.3](cpp-map/07-storage-formats/mds-tables.md#33-table-server--client-the-generic-two-phase-commit)
- **Snap trace**: the encoded chain of realm descriptors (seq, created, parent, snapshots, past-parent snapshots) from a realm up to the root or the global realm, sent in replies, `MClientSnap` and cap imports. → [snapshots 3.3](cpp-map/10-snapshots-quotas-subvolumes/snapshots.md#33-snap-traces-seen-by-clients)
- **`SnapContext`**: the (seq, snapshot list) pair that every writer, client or MDS, attaches to OSD writes so that RADOS self-managed snapshots clone objects before overwriting them; clients build it from snap traces. → [snapshots 1](cpp-map/10-snapshots-quotas-subvolumes/snapshots.md#1-purpose-and-responsibilities), [RADOS and OSD 3.10](cpp-map/07-storage-formats/rados-and-osd-interactions.md#310-snapshots-and-osd-snap-trimming)
- **Snapdiff and blockdiff**: the request ops `READDIR_SNAPDIFF` and `FILE_BLOCKDIFF` that cephfs-mirror uses to list the entries and the data blocks that changed between two snapshots. → [snapshots 3.14 and 3.15](cpp-map/10-snapshots-quotas-subvolumes/snapshots.md#314-readdir_snapdiff-used-by-cephfs-mirror)
- **Snapflush (cap snap)**: after a snapshot, a client that had buffered writes keeps a "cap snap" and later flushes the per-snapshot metadata (`FLUSHSNAP`); the MDS waits for these flushes before serving the snapped inode. → [capabilities 3.11](cpp-map/02-client-protocol/capabilities.md#311-snapshots-snapflush)
- **snapid**: a 64-bit snapshot id (`snapid_t`); `CEPH_NOSNAP` (-2) means the live "head" version and `CEPH_SNAPDIR` (-1) the `.snap` pseudo-directory (`src/include/rados.h:38-39`). Ids are global to the file system and monotonically increasing. → [snapshots 1](cpp-map/10-snapshots-quotas-subvolumes/snapshots.md#1-purpose-and-responsibilities)
- **`snaplock`**: inode `SimpleLock` (`CEPH_LOCK_ISNAP`) for the snaprealm; path traversal rdlocks it on every ancestor, and mksnap, rmsnap and link, unlink or rename of the inode xlock it. → [lock types 3.2](cpp-map/05-locking/lock-types-and-state-machines.md#32-lock-types-per-object)
- **Standby**: an idle daemon in the FSMap's shared pool, without a rank, that the monitor can promote to a failed or new rank. → [FSMap and MDSMap 3.6](cpp-map/01-cluster-integration/fsmap-and-mdsmap.md#36-standby-selection)
- **Standby-replay**: a daemon assigned to follow an active rank's journal read-only, keeping a warm cache so that it can take the rank over quickly. → [MDLog 3.16](cpp-map/06-journal/mdlog-and-journaler.md#316-standby-replay-tailing-and-takeover), [rank lifecycle 3.9](cpp-map/09-recovery/rank-lifecycle-and-recovery.md#39-replay-and-standby-replay)
- **Stopping (`up:stopping`)**: the state of a rank that is being removed (for example after `max_mds` is lowered): it exports its subtrees and strays, closes sessions, trims and caps its journal, and ends in `down:stopped`. → [rank lifecycle 3.19](cpp-map/09-recovery/rank-lifecycle-and-recovery.md#319-stopping-upstopping--downstopped)
- **Stray**: an inode whose last primary name was removed. Its dentry moves to one of the rank's ten stray directories (`~mdsN/stray0` to `stray9`, inodes `0x600 + 10*rank + i`), where it stays while referenced (open files, caps, snapshots) and from which it is purged, reintegrated or migrated. → [strays and purge 3.0 and 3.1](cpp-map/11-background-services/strays-and-purge.md#30-lifecycle-overview)
- **Subtree, subtree root and bound**: the namespace is partitioned into subtrees whose roots are dirfrags with an explicit `dir_auth` (authority pair); everything below a root inherits its authority down to the nested subtree roots, called bounds. `MDCache::subtrees` maps each root to its bounds. → [subtrees 3.2](cpp-map/04-cache/mdcache-subtrees-traversal-replication.md#32-the-subtree-map)
- **Subvolume**: a directory with `ceph.dir.subvolume=1`, recorded as the `SUBVOLUME` flag of its snaprealm. Renames and links across subvolumes return `EXDEV`, nested subvolumes are refused, and every inode below reports the root's inode number as its `subvolume_id`, which clients use for per-subvolume metrics (`src/mds/CInode.cc:5597 (CInode::get_subvolume_id)`); mgr/volumes creates them. → [rstats 3.12 and 3.13](cpp-map/10-snapshots-quotas-subvolumes/rstats-quotas-and-subvolumes.md#312-subvolumes-the-subvolume-realm-flag)

## T

- **Trace (`InodeStat`, `DirStat`, `LeaseStat`)**: the records in an `MClientReply` that describe the target, its parent directory and dentry. `InodeStat`, encoded by `CInode::encode_inodestat` (`src/mds/CInode.cc:3959`), carries attributes, the caps granted to the client, snapshot and quota data; read replies are the main way clients obtain caps. → [wire protocol 3.9](cpp-map/02-client-protocol/wire-protocol.md#39-mclientreply-encoding), [lookup 3.4](cpp-map/03-request-path/lookup-readdir-open-and-file-locks.md#34-what-a-trace-carries-and-which-caps-are-issued-cinodeencode_inodestat)
- **Two-phase commit and witnesses**: the protocol of cross-rank link, unlink, rmdir and rename. The leader (the rank executing the request; for rename, the auth of the destination dentry) sends prepares to witnesses, which journal `EPeerUpdate` PREPARE; the leader journals `EUpdate` with `had_peers`, then `ECommitted`. An interrupted one is decided in resolve. → [rename 3.8](cpp-map/03-request-path/rename.md#38-witness-selection-and-the-two-phase-commit-leader-side), [resolve and rejoin 3.4](cpp-map/09-recovery/resolve-and-rejoin.md#34-resolve-step-1-peer-resolves-two-phase-commit-outcomes)

## V

- **Version and `pre_dirty`**: each dirfrag keeps a projected version counter; every mutation takes the next value for each dentry and child inode it changes (`pre_dirty`), so an inode's version comes from its parent dirfrag. Dirty objects record the version they need written. → [cdir 3.8](cpp-map/04-cache/cdir-cdentry-and-cache-objects.md#38-versions-projection-and-dirty-tracking), [cinode 3.8](cpp-map/04-cache/cinode-and-inode-types.md#38-versions)
- **`versionlock`**: the local lock of inodes and dentries that pipelines projected versions; the leader wrlocks it next to xlocks of other locks, and peers xlock it. → [lock types 3.2](cpp-map/05-locking/lock-types-and-state-machines.md#32-lock-types-per-object)
- **Virtual xattrs (vxattrs)**: `ceph.*` extended attributes. The MDS serves and sets some of them (layouts, quotas, pins, subvolume flag, charmap, quiesce block); most read-only ones, such as `ceph.dir.rbytes`, are synthesized by clients from `InodeStat`. → [attributes and xattrs 3.8 to 3.10](cpp-map/03-request-path/attributes-and-xattrs.md#38-virtual-xattrs-set-and-remove-srcmdsservercc6342-serverhandle_client_setvxattr)

## W

- **Waiter**: an `MDSContext` registered on a cache object or lock with a wait mask, completed when the awaited state change happens; it usually re-dispatches the request that was waiting (`src/mds/MDSContext.h:38`). → [cdir 3.7](cpp-map/04-cache/cdir-cdentry-and-cache-objects.md#37-waiters)

## X

- **`xattrlock`**: inode `SimpleLock` (`CEPH_LOCK_IXATTR`) for the xattr map and its version; it carries the `Xs`/`Xx` caps. → [lock types 3.2](cpp-map/05-locking/lock-types-and-state-machines.md#32-lock-types-per-object)
- **`Xs` / `Xx`**: the cap bits of `xattrlock` (shift 6): shared lets a client cache the xattr blob, exclusive lets it change xattrs locally and flush the whole blob later. → [capabilities 3.1](cpp-map/02-client-protocol/capabilities.md#31-the-cap-bit-model)
