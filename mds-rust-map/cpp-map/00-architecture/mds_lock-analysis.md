## Summary

- **What it is.** `mds_lock` is one `ceph::fair_mutex` per `ceph-mds` process, owned by `MDSDaemon` (`src/mds/MDSDaemon.h:74 (MDSDaemon::mds_lock)`) and referenced by `MDSRank` (`src/mds/MDSRank.h:414 (MDSRank::mds_lock)`). It is a FIFO ticket lock whose every unlock wakes all waiters (`src/common/fair_mutex.h:24-50 (ceph::fair_mutex::lock)`), and it is also the mutex of the daemon timer (`src/mds/MDSDaemon.cc:87 (MDSDaemon::MDSDaemon)`). A process serves at most one rank, so process-wide and rank-wide are the same thing.
- **What it protects.** All metadata state of the rank: cache objects and their projections, versions, pins, waiters and lock state machines; caps and leases; sessions and the SessionMap; journal segment bookkeeping; InoTable, snap table client and server, OpenFileTable; strays, scrub, migration, balancer, quiesce and quarantine state; the MDSMap pointer, rank state, waiter queues and timer schedule. No per-inode, per-dirfrag, per-subtree, per-session or per-table mutex exists on the metadata path. The few private mutexes guard hand-off queues or side systems, never cache objects ([1.6](#16-other-locks-and-their-order)).
- **Who takes it.** 21 entry paths on about 20 threads: message dispatch and connection events, every journal and RADOS completion, the timer (held during every callback), the progress thread, the cache-upkeep and log-trim threads (each holds it for a whole pass), replay and journal recovery, the PurgeQueue finisher, quiesce, metrics and dmClock threads, admin-socket and tell commands, signals ([1.2](#12-entry-points)).
- **Consequence.** All metadata CPU work of a rank runs while holding this one mutex, so at most one core does metadata work at any instant, whatever the number of clients or subvolumes. Only message decode/encode and authentication, journal event encoding and append, journal read and decode during replay, dirfrag-commit and backtrace op encoding, purge execution, and beacon and metrics bookkeeping run in parallel ([1.5](#15-work-that-runs-outside-mds_lock)). A few accesses to lock-protected state happen without the lock (journal segment bookkeeping on the submit and replay threads, the `status` command's MDSMap reads, a cache trim from the replay thread after a journal read error); [1.5](#15-work-that-runs-outside-mds_lock) lists them.
- **Serialization points.** The 665 staging entries collapse to 268 distinct serialization points ([section 3](#3-consolidated-serialization-points)). 116 are implementation artifacts, 112 are partly required (some ordering is needed, at a narrower scope than C++ uses) and 40 are inherent. 35 of the 40 process-wide points are artifacts. The inherent conflicts are almost all per inode, per dentry, per (inode, client) cap, per session, or imposed by the unmodified monitor, OSDs and clients.
- **Rank-wide singletons couple subvolumes** ([section 4](#4-rank-wide-singletons-that-couple-independent-subvolumes)): one journal stream (whole-log flushes, segment-granular trimming), the SessionMap version chain (completions of different clients must apply in projection order, enforced by an assertion), the InoTable, the current stray directory, the PurgeQueue, the OpenFileTable, the LRU and memory budget, Locker bookkeeping lists, the dispatch and finisher threads, the Objecter epoch barrier and MetricsHandler. Across ranks: the snap table and the global snap seq on the table-server rank, and the QuiesceDb leader.
- **Two creates in one directory** ([5.a](#5a-two-clients-create-projecta-and-projectb)) never conflict on an object lock (distinct dentry xlocks, shared directory wrlocks). They still serialize on `mds_lock` and the dispatch thread, the directory dirfrag version counter and projected-fnode FIFO, the directory inode projection FIFO, the root dirfrag fnode, the journal stream, in-order completion on one finisher thread and the rank-wide SessionMap projected version. A reader of the directory forces a lock transition that makes both wait.
- **What remains with perfect locking** ([section 6](#6-coupling-that-would-remain-even-with-perfect-locking)): recursive stats and quotas aggregate up to `/volumes` and `/`; snapshot ids are file-system-wide (OSD snap contexts) and the C++ global snap seq stamps every new dentry; sessions, counted-message ordering and caps on shared ancestors span subvolumes; hard links stop at subvolume boundaries (`EXDEV`) but still need lookup by inode number and stray reintegration; unlinked-but-open files need a stray home; inode numbers are client-visible and unique per file system.
- **Observability** ([section 7](#7-observing-mds_lock-contention-today)): there is no contention counter. Contention shows as `finisher-MDSRank` queue length and completion latency, `throttle-msgr_dispatch_throttler-mds`, `mds.reply_latency`, op-tracker gaps (`dispatched` to the first MDS event, `journal_committed:` to `replying`), heartbeat timeouts and skipped beacons.

## 1. What `mds_lock` is and how code enters it

### 1.1 Definition and rules

| Fact | Code |
|---|---|
| Declared `ceph::fair_mutex mds_lock{"MDSDaemon::mds_lock"}` in `MDSDaemon`. `MDSRank` keeps a reference, "so that users of MDSRank don't carry around references to the outer MDS, and we can substitute a separate lock here in future potentially". | `src/mds/MDSDaemon.h:74 (MDSDaemon::mds_lock)`, `src/mds/MDSRank.h:411-414 (MDSRank::mds_lock)` |
| FIFO ticket lock. `lock()` takes ticket `next_id++` and waits on a condition variable until `unblock_id` equals it. `unlock()` increments `unblock_id` and calls `notify_all()`. There is no barging, recursion or priority, and every release wakes every waiter. | `src/common/fair_mutex.h:24-50 (ceph::fair_mutex::lock, unlock)` |
| The daemon `SafeTimer` is constructed on `mds_lock` with safe callbacks: its thread holds `mds_lock` while it runs each due callback. | `src/mds/MDSDaemon.cc:87 (MDSDaemon::MDSDaemon)`, `src/common/Timer.cc:80-111 (CommonSafeTimer::timer_thread)` |
| Header rule: whoever takes the lock must check `stopping`. If it is set, the holder either does nothing and drops the lock, or never drops it again (respawn). | `src/mds/MDSDaemon.h:70-75 (MDSDaemon::mds_lock)` |
| `MDSContext::complete` asserts the caller holds the lock and resets the heartbeat. `MDSIOContextBase::complete` takes the lock itself, drops the completion if the daemon is shutting down (`MDSRank::is_daemon_stopping()`, the flag set by `MDSRankDispatcher::shutdown`, not the `up:stopping` rank state), and respawns on `-EBLOCKLISTED`/`-ETIMEDOUT`. | `src/mds/MDSContext.cc:24-31 (MDSContext::complete)`, `src/mds/MDSContext.cc:95-118 (MDSIOContextBase::complete)`, `src/mds/MDSRank.cc:1598-1601 (MDSRank::is_daemon_stopping)` |
| Lock-held assertions compile to `true` unless `CEPH_DEBUG_MUTEX` is defined. `fair_mutex` has no contention or hold-time instrumentation. | `src/common/ceph_mutex.h:138`, `src/common/ceph_mutex.h:142-198`, `src/common/fair_mutex.h:58-81 (ceph::fair_mutex::is_locked_by_me)` |
| The `MDSRank` heartbeat handle is reset by code holding the lock (`heartbeat_reset`, also called from every `MDSContext::complete`), with one exception: `CDir::_omap_commit_ops` resets it from `mds-rank-fin` without the lock while it encodes a large dirfrag commit, so a commit in progress can keep beacons flowing while another thread holds `mds_lock`. If no reset happens within `mds_heartbeat_grace` (15 s), the beacon thread stops sending beacons. | `src/mds/MDSRank.cc:505 (MDSRank::MDSRank)`, `src/mds/MDSRank.cc:1359-1375 (MDSRank::heartbeat_reset)`, `src/mds/CDir.cc:2543 (CDir::_omap_commit_ops)`, `src/mds/CDir.cc:2594 (CDir::_omap_commit_ops)`, `src/mds/Beacon.cc:203-210 (Beacon::_send)` |

The chains are `<uuid>` → `A` → `g` → `/volumes` → `/` and `<uuid>` → `B` → `g` → `/volumes` → `/`, so `g`, `/volumes`, `/` and their dirfrags are projected and journaled by both subvolumes' flushes, rate-limited by that interval. [R59](#33-rank) [P18](#32-global-process-the-whole-rank) [P16](#32-global-process-the-whole-rank)

**Why the two subvolumes collapse onto one core today**

- Except for decoding, the CPU work of every step above runs on `ms_dispatch` or `mds-rank-fin` while holding `mds_lock`, and the upkeep and trim threads take turns on the same FIFO lock. At any instant at most one thread does metadata work for both subvolumes together.
- The single journal turns each fsync, and each `max_size` step, into a flush of both subvolumes' buffered events, and the completions run on one thread in offset order.
- The ancestors `g`, `/volumes` and `/` are projected, journaled and later committed on behalf of both subvolumes, each inode at most once per second and each dirfrag whenever a child inode below it propagates. The dirfrags touched on every flush (the file's parent `<uuid>` and grandparent `A` or `B`) belong to one subvolume each.
- The data path itself does not involve the MDS (writes go to the OSDs, and `O_SYNC` only flushes data, see the [libcephfs page](../02-client-protocol/libcephfs-fuse-ganesha-expectations.md)); every fsync of dirty size/mtime and every `max_size` step does.

## 6. Coupling that would remain even with perfect locking

These couplings do not come from `mds_lock`; they come from the data model, POSIX, or the protocols of the unmodified peers (kernel client, libcephfs/ceph-fuse/NFS-Ganesha, monitors, OSDs, `mgr/volumes`). "Imposed by" separates what an external party depends on from what is internal to the C++ MDS (its on-disk layout, journal and MDS-to-MDS protocol).

### 6.1 Recursive statistics and quotas up to the root

- **Fact.** `rstat` (`rbytes`, `rfiles`, `rsubdirs`, `rsnaps`, `rctime`) of a directory is the sum (max for `rctime`) over its subtree, and every mutation's delta must eventually reach every ancestor. C++ applies it eagerly to the parent, and to higher ancestors at most once per `mds_dirstat_min_interval`; otherwise it defers through dirty scatterlocks and gathers (`src/mds/MDCache.cc:2264-2476 (MDCache::predirty_journal_parents)`, `src/mds/Locker.cc:5404 (Locker::scatter_nudge)`). [T8](#34-subtree) [I2](#36-inode)
- **Consumers above a subvolume.** `ceph.dir.rbytes`/`rentries`/`rctime` vxattrs on any directory; a directory's `st_size` when clients report `rbytes` (libcephfs `client_dirsize_rbytes`, default true; kclient `rbytes` mount option); group quotas on `/volumes/<group>`; `statfs` from the nearest quota realm at or above the mount root; `mgr/volumes` usage reporting (`subvolume info` `bytes_used`, `resize --no_shrink`, clone progress); the `mds.root_rbytes`/`root_rfiles` gauges (`src/mds/MDCache.cc:302-304 (MDCache::log_stat)`). Details: [rstats, quotas and subvolumes, 3.15 and 6](../10-snapshots-quotas-subvolumes/rstats-quotas-and-subvolumes.md).
- **Quotas.** Enforcement is client-side, from the quota realm inode's rstat that the MDS pushes with `MClientQuota` (thresholds at 7/8 of the limit and 1/16 of the headroom) (`src/mds/MDCache.cc:2103-2180 (MDCache::broadcast_quota_to_client)`). The subvolume quota sits on `<uuid>` inside the subvolume, so it only needs propagation within the subvolume; a group quota needs aggregation across the subvolumes of the group. [I28](#36-inode)
- **Exactness.** No consumer requires synchronous exactness above the immediate parent; C++ itself is only eventually consistent there. A directory's own `dirstat` (entry counts, mtime, ctime) is exact when read through its `filelock` rdlock. [I1](#36-inode)
- **Imposed by:** client-visible vxattrs and `stat` (kclient, libcephfs), client-side quota enforcement (kclient, libcephfs), `mgr/volumes`. The propagation mechanism (projection chains, scatterlocks, journaling ancestors) is C++ internal.

### 6.2 Snapshots and the global snaprealm

- **Snapids are global.** Every snapshot id is unique and monotonic per file system and is allocated by the table server on one rank through a 2PC (`src/mds/MDSTableServer.cc:111-174 (MDSTableServer::handle_prepare, MDSTableServer::_prepare_logged)`); the OSDs see them in every write's SnapContext, and removed snaps are reported to the monitor (`src/mds/SnapServer.cc:365 (SnapServer::check_osd_map)`). [C15](#31-global-cluster-and-file-system) [C16](#31-global-cluster-and-file-system)
- **Realms span subtrees.** A snapshot of a directory applies to its whole subtree: creating it splits the parent realm and moves every capped inode below (`src/mds/SnapRealm.cc:338 (SnapRealm::split_at)`), clients receive the new realm before the reply (`src/mds/Server.cc:11764 (Server::_mksnap_finish)`), and every inode below copies on its next write. `mgr/volumes` takes subvolume snapshots at the subvolume base directory and refuses group snapshots, but on a file system that allows snapshots any client whose MDS caps include `s` for `/` or `/volumes` can snapshot them, which covers every subvolume below. [T3](#34-subtree) [T5](#34-subtree) [S11](#38-session)
- **Global realm.** Hard-linked inodes outside subvolumes are placed in the global snaprealm (`PARENT_GLOBAL`, `src/mds/Server.cc:8035-8040 (Server::_link_local)`); its seq is the file-system-wide `max(last_created, last_destroyed)` (`src/mds/SnapRealm.cc:125-131 (SnapRealm::check_cache)`), and updates are broadcast to every session (`src/mds/MDCache.cc:10348-10361 (MDCache::notify_global_snaprealm_update)`). Inside a subvolume, hard links do not join it. [C18](#31-global-cluster-and-file-system)
- **Global seq as dentry `first`.** Every new dentry gets `first = global newest seq + 1` (`src/mds/Server.cc:4046 (Server::rdlock_path_xlock_dentry)`) and COW decisions use the global seq (`src/mds/MDCache.cc:1708-1759 (MDCache::journal_cow_dentry)`), partially relaxed by `mds_use_global_snaprealm_seq_for_subvol` (`src/mds/MDCache.cc:204 (MDCache::MDCache)`). [C17](#31-global-cluster-and-file-system)
- **Imposed by:** the OSD snapshot model (SnapContext seq and snap list per write, pool snap removal), the kclient/libcephfs snap trace and realm semantics, the `mgr/volumes` snapshot layout. The single table server, the full-table NOTIFY_PREP, and using the global seq for every dentry are C++ internal. See [snapshots](../10-snapshots-quotas-subvolumes/snapshots.md) and [MDS tables](../07-storage-formats/mds-tables.md).

### 6.3 Client sessions that span subvolumes

- **Fact.** A session is per (client entity, rank) (`src/mds/SessionMap.h:568 (SessionMapStore::session_map)`). A kernel or ceph-fuse mount of `/`, or one NFS-Ganesha mount exporting several subvolumes, has one session per rank that covers many subvolumes ([libcephfs page, section 6](../02-client-protocol/libcephfs-fuse-ganesha-expectations.md#6-concurrency-and-mds_lock)).
- **Per-session state that couples subvolumes:** counted-message order (`push_seq`) over all inodes of the session, which `REQUEST_CLOSE` checks (`src/mds/MDSRank.cc:1551-1561 (MDSRank::send_message_client_counted)`); `completed_requests` trimmed by `oldest_client_tid`, so one stuck request pins the whole list; `completed_flushes`; one pool of preallocated and delegated inode numbers; one cap TTL and `cap_gen` (a late RENEWCAPS invalidates every cap of the session on the client, `src/client/Inode.cc:242 (Inode::cap_is_valid)`); eviction blocklists the client address and kills every cap of the session (`src/mds/MDSRank.cc:3951-4046 (MDSRank::evict_client)`); reconnect and reclaim are per session but gate the whole rank's phase. [S3](#38-session) [S2](#38-session) [S8](#38-session) [S5](#38-session) [S10](#38-session) [R11](#33-rank) [R12](#33-rank)
- **Imposed by:** the client session protocol (kclient, libcephfs) and OSD blocklisting by address.

### 6.4 Caps on shared ancestors

- **Fact.** libcephfs mount sends `GETATTR` for the mount root and every ancestor up to `/` (`src/client/Client.cc:7100-7117 (Client::mount)`). Every reply with a dentry trace also encodes the parent directory's inode stat (`src/mds/Server.cc:2529 (Server::set_trace_dist)`), and `encode_inodestat` creates a cap for the client when it has none (`src/mds/CInode.cc:4208-4213 (CInode::encode_inodestat)`). Clients of different subvolumes therefore hold caps on `/`, `/volumes` and `/volumes/<group>`.
- **Consequence.** A lock-state change on such a directory (namespace changes in `/volumes` or a group directory by `mgr/volumes`; quota, layout or pin changes on a group directory; a snapshot on an ancestor) gathers revocations from every client whose issued caps conflict (`src/mds/CInode.cc:3912 (CInode::issued_caps_need_gather)`, `src/mds/Locker.cc:1299 (Locker::eval_gather)`). Clients holding only `p` (pin) do not conflict with most transitions. [I4](#36-inode) [F18](#35-dirfrag)
- **Ancestor locks.** Separately, every path-based request rdlocks the `snaplock` of every ancestor up to `/` and keeps it until the safe reply, so a `snaplock` xlock on an ancestor (mksnap, subvolume or quota realm creation, directory rename) waits for all in-flight requests below it, unsafe ones included (`src/mds/Locker.cc:157 (Locker::try_rdlock_snap_layout)`, `src/mds/Locker.cc:926-930 (Locker::handle_locks_for_early_reply)`). [T1](#34-subtree) [T2](#34-subtree)
- **Imposed by:** the client cap protocol and POSIX visibility. The per-request rdlock of every ancestor is a C++ choice; what is required is that a snapshot or realm change has a consistent cut.

### 6.5 Hard links

- **Across subvolumes: forbidden.** `link` returns `EXDEV` when the target's realm belongs to another subvolume (`src/mds/Server.cc:7972-7982 (Server::handle_client_link)`), and so does `rename` (`src/mds/Server.cc:9556-9563 (Server::handle_client_rename)`); the kclient also returns `EXDEV` for renames across quota realms ([kclient page](../02-client-protocol/kclient-expectations.md)).
- **Inside a subvolume, or outside subvolumes: allowed.** A remote dentry names the primary inode by number, and the primary may live in another directory, subtree or rank, found through backtraces and `open_ino` (`src/mds/MDCache.cc:9591 (MDCache::open_ino)`). When the primary link is removed while other links remain, the inode moves to a stray directory and is later reintegrated by an internal rename, which is a 2PC if cross-rank (`src/mds/StrayManager.cc:679 (StrayManager::reintegrate_stray)`). Outside subvolumes the inode also joins the global realm (6.2). [I36](#36-inode) [I45](#36-inode)
- **Imposed by:** POSIX `link(2)`/`rename(2)`; `EXDEV` is a permitted POSIX error, and confining links to a subvolume is Ceph policy that `mgr/volumes` relies on.

### 6.6 Per-rank stray directories

- **Fact.** Each rank has ten stray directories `~mdsN/strayK` (`src/mds/mdstypes.h:34`, `src/mds/mdstypes.h:49`). Every primary unlink or rename-over on the rank, from any subvolume, relinks the inode into the current one (`src/mds/Server.cc:3595-3631 (Server::prepare_stray_dentry)`), which rotates with each log segment (`src/mds/MDCache.cc:776-800 (MDCache::advance_stray)`). The inode's rstat leaves the subvolume (and its quota) at once and lands under `~mdsN`. An unlinked-but-open file stays there until its last cap is released, and a stopping rank exports its strays to rank 0 (`src/mds/MDCache.cc:8236 (MDCache::shutdown_export_strays)`). [R50](#33-rank) [R53](#33-rank)
- **Imposed by:** POSIX unlink-while-open semantics (the inode outlives its last name) and RADOS deletion of data objects named after the inode. Where unlinked inodes are kept, and that this is per rank, is C++ internal (`~mdsN` is not visible to clients).

### 6.7 Per-rank inode-number allocation

- **Fact.** Rank r allocates from `[(r+1)<<40, (r+2)<<40)` (`src/mds/InoTable.cc:29-44 (InoTable::reset_state)`). Sessions receive batches of `mds_client_prealloc_inos` (1000), and async-create capable kernel clients receive delegated ranges (`src/mds/Server.cc:2591-2614 (Server::set_reply_extra_bl)`). [R32](#33-rank) [S8](#38-session)
- **Client-visible.** Inode numbers are `st_ino`, are carried in NFS file handles (resolved with `LOOKUPINO` after a restart), are chosen by kernel clients for async creates from delegated ranges, and name the data objects (`<ino>.<objno>`) in the data pools ([RADOS object catalog](../07-storage-formats/rados-object-catalog.md)). They must be unique per file system and never reused while referenced. Lookup by number needs an index (backtraces, `open_ino`, peer search), which in C++ waits for every in rank to be active (`src/mds/MDCache.cc:9414-9447 (MDCache::do_open_ino_peer)`). [C11](#31-global-cluster-and-file-system)
- **Imposed by:** the clients (inode numbers in replies, delegated ranges, NFS handles) and the data-pool object naming read by clients and OSD tools. A per-rank table with one version chain is C++ internal.

### 7.2 Op tracker

`dump_ops_in_flight`, `dump_blocked_ops`, `dump_historic_ops` and `dump_historic_ops_by_duration` run without `mds_lock` (`src/mds/MDSRank.cc:2688-2815 (MDSRankDispatcher::handle_asok_command)`). Each client request carries these events:

- `header_read`, `throttled`, `all_read` at receipt, and `dispatched`, stamped by `Messenger::ms_deliver_dispatch` before `MDSDaemon::ms_dispatch2` takes `mds_lock` (`src/common/TrackedOp.h:211-214`, `src/msg/Messenger.h:758-759 (Messenger::ms_deliver_dispatch)`). The gap `all_read` → `dispatched` is time spent queued for the dispatch thread.
- The next event is marked under the lock, typically `acquired locks` or `failed to ...` from `acquire_locks` (`src/mds/Locker.cc:410-664 (Locker::acquire_locks)`). The gap `dispatched` → that event is mostly `mds_lock` wait.
- `journal_committed: ` is marked in `ServerLogContext::pre_finish` on `mds-rank-fin` before `mds_lock` is taken (`src/mds/Server.cc:174-177 (ServerLogContext::pre_finish)`, `src/mds/MDSContext.cc:122-127 (MDSLogContextBase::complete)`), and `replying` after it is taken (`src/mds/Server.cc:2388 (Server::reply_client_request)`). That gap is the completion's `mds_lock` wait plus the completion's own work before the reply (applying projections, sending dentry links).
- `ops --flags=locks` dumps per-request lock sets but takes `mds_lock`, and `op get` takes it with or without flags (`src/mds/MDSRank.cc:2697-2708 (MDSRankDispatcher::handle_asok_command)`, `src/mds/MDSRank.cc:2743-2758 (MDSRankDispatcher::handle_asok_command)`).

### 7.4 Tools and practice

- Admin commands that need `mds_lock` queue behind it and also block the single admin-socket thread: `status` (`src/mds/MDSDaemon.cc:259 (MDSDaemon::dump_status)`), `session ls`, `dump cache`, `ops --flags=locks`. During contention, use `perf dump`, `dump_ops_in_flight`, `dump_historic_ops` and `config show`, which do not take it.
- `ceph daemon mds.<id> lockup <ms>` holds `mds_lock` deliberately, for testing (`src/mds/MDSDaemon.cc:168-178 (MDSDaemon::asok_command)`).
- Threads are named (`ms_dispatch`, `mds-rank-fin`, `mds-rank-progr`, `safe_timer`, `mds-cache-trim`, `mds-log-trim`, ...; see the [thread inventory](process-and-threading.md#35-thread-inventory)), so per-thread CPU accounting (for example `top -H`) shows which lock holder is busy. A stack sample of a contended daemon shows the waiting threads inside `ceph::fair_mutex::lock` (`src/common/fair_mutex.h:24-32`). The dmClock threads are unnamed and inherit the creator's name; they are started from the `MDSRank` constructor, which runs while `ms_dispatch` handles the MDSMap that assigns the rank, so they appear as `ms_dispatch` (`src/mds/MDSDmclockScheduler.h:445-447 (MDSDmclockScheduler::MDSDmclockScheduler)`, `src/mds/MDSDaemon.cc:940 (MDSDaemon::handle_mds_map)`). The PurgeQueue, MonClient and MgrClient timers likewise appear as `safe_timer`.

## 8. Method and verification

- **Sources.** The `serialization_points` arrays of all 42 staging files (665 entries), section 6 of all 42 pages under `cpp-map/`, and the code at commit `5f7e383ae6d`.
- **Entry points.** Every `mds_lock` reference in `src/mds` (lock guards, `lock()`/`unlock()`, the dmClock `mds_lock()` wrapper, assertions), every `MDSIOContextBase` completion path, the timer, and the `add_event_after` users were inspected; [1.2](#12-entry-points) lists the acquisition sites.
- **Deduplication.** Each staging entry was assigned to exactly one row of [section 3](#3-consolidated-serialization-points) (665 entries → 268 rows; the assignment was checked mechanically for completeness and uniqueness). Rows merge entries that describe the same mechanism; the "Pages" column links every page that reported it. When staging entries disagreed on scope or inherence, the row states the value supported by the code: "scope" is the breadth of the serialization as implemented, and "true conflict" is the narrowest scope at which operations really conflict.
- **Citations.** Every `path:line (Symbol)` on this page was checked by script: the file exists, the line range is inside it, and the symbol occurs at the cited lines or in the enclosing function. Python and kernel citations were checked by hand or taken from the kclient page (the kernel tree is not in this repository).
- **Not verified at runtime.** Items marked "inferred" or "by code reading" in the source pages (possible deadlocks in `MDSDaemon::suicide` and in metrics shutdown, the `CDir::_omap_commit_ops` fnode race, the dmClock lock inversion) are reported as such and were not reproduced. The same holds for the items added by the fact-check pass: the inline `-EROFS` completion of a read-only PurgeQueue ([1.2](#12-entry-points), row 16), the `volume_info_lock` re-entry in dmClock `cancel_inflight_request` ([1.6](#16-other-locks-and-their-order)), the unlocked `standby_trim_segments()` call and segment bookkeeping in the replay thread (row 14), the unlocked `LogSegment::offset`/`end` writes of `mds-log-submit` and the unlocked `mdsmap` reads of the `status` command ([1.5](#15-work-that-runs-outside-mds_lock)). How NFS-Ganesha maps NFS `COMMIT` and stable writes onto libcephfs calls is outside this repository, and the kernel client's request path format (`build_dentry_path`, `build_inode_path`) is marked unverified because the kernel tree is not in this repository; the libcephfs format was checked.
- **Fact-check pass.** Every section was re-checked against the tree at `5f7e383ae6d`; corrected statements and added citations were checked with the same script.
